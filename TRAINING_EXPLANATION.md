# Как работает обучение и запуск модели

В проекте есть две разные части:

1. обучение — модель учится лучше отвечать на технические вопросы;
2. инференс — уже обученная модель отвечает на новые запросы через API.

Общая схема выглядит так:

```text
train.jsonl
    ↓
базовая Qwen-модель
    ↓ обучение LoRA-адаптера
my_docker_lora_adapter_3b/
    ↓ подключение к базовой модели через vLLM
Google Colab + T4 GPU
    ↓ ngrok
локальный worker → FastAPI → клиент
```

## 1. Подготовка датасета

`train.jsonl` — это файл формата JSON Lines. В нём каждая строка является отдельным примером для обучения: вопросом, ответом или диалогом.

Примеры посвящены backend- и DevOps-темам: Docker, FastAPI, базы данных, асинхронность и другим технологиям.

Модель не запоминает файл буквально. Во время обучения она видит примеры и постепенно корректирует обучаемые параметры так, чтобы чаще выдавать ответы в нужном стиле и с нужным уровнем технической точности.

Важно: качество результата сильно зависит от датасета. Если в примерах есть ошибки, модель может начать воспроизводить и эти ошибки.

## 2. Базовая модель

В качестве основы используется `Qwen/Qwen2.5-3B-Instruct`.

Это уже предварительно обученная и настроенная на инструкции языковая модель. Она умеет отвечать на разные вопросы ещё до нашего обучения.

Мы не обучаем её с нуля. Мы берём готовую модель и добавляем к ней небольшой специализированный слой, который помогает адаптировать поведение под наши темы.

Упрощённая аналогия:

```text
Базовая модель = общий опыт и знания
LoRA-адаптер   = дополнительная специализация по Docker, FastAPI и DevOps
```

## 3. Что такое LoRA и QLoRA

### Полное дообучение

При обычном fine-tuning изменяются практически все параметры модели. Для модели на несколько миллиардов параметров это требует много видеопамяти и времени.

```text
3B параметров → нужно хранить и обновлять огромный набор весов
```

Для Colab T4 с 16 ГБ видеопамяти такой подход неудобен и может привести к ошибке `Out Of Memory`.

### LoRA

LoRA замораживает базовую модель. Её исходные веса не изменяются.

В отдельные слои модели добавляются небольшие обучаемые матрицы. В вашем коде это слои внимания и MLP-блоки:

```text
q_proj, k_proj, v_proj, o_proj
gate_proj, up_proj, down_proj
```

Во время обучения меняются только эти маленькие матрицы. Поэтому:

- требуется значительно меньше памяти;
- обучение проходит быстрее;
- адаптер занимает гораздо меньше места;
- одну базовую модель можно использовать с разными адаптерами.

После обучения модель концептуально выглядит так:

```text
итоговый ответ = базовая Qwen-модель + LoRA-адаптер
```

### QLoRA

QLoRA — это сочетание LoRA и квантования базовой модели. Квантование хранит веса модели в формате с меньшей точностью, например 4-bit, чтобы дополнительно экономить видеопамять.

В установке проекта присутствуют `bitsandbytes` и `torchao`, которые используются для оптимизации работы с памятью. Однако в показанном фрагменте обучения модель загружается так:

```python
torch_dtype=torch.float16
```

и отдельный `BitsAndBytesConfig(load_in_4bit=True, ...)` не задан. Поэтому технически текущий код ближе к обычному LoRA fine-tuning в `float16`, а не к полноценному 4-битному QLoRA.

Это не отменяет пользу LoRA: обучаются всё равно только адаптеры. Но если нужно именно QLoRA, загрузку модели надо дополнить 4-битной конфигурацией bitsandbytes.

## 4. Что делает `SFTTrainer`

`SFTTrainer` из библиотеки TRL организует обучение на текстовых примерах.

В вашем коде задаются основные параметры:

- `num_train_epochs=3` — пройти по датасету три раза;
- `per_device_train_batch_size=2` — обрабатывать по два примера за шаг;
- `gradient_accumulation_steps=4` — накапливать градиенты четырёх шагов перед обновлением;
- `learning_rate=2e-4` — размер изменения параметров адаптера;
- `max_length=512` — ограничение длины последовательности;
- `fp16=True` — использовать вычисления в half precision.

Один цикл обучения выглядит примерно так:

```text
пример из train.jsonl
    ↓
токенизатор превращает текст в числа
    ↓
модель строит ответ
    ↓
сравнение ответа модели с правильным текстом
    ↓
ошибка распространяется назад
    ↓
обновляются только LoRA-матрицы
```

`epoch` — это один полный проход по всему датасету. Три эпохи означают, что каждый пример был использован трижды.

## 5. Сохранение результата

После выполнения:

```python
trainer.train()
```

сохраняется адаптер:

```python
adapter_path = "./my_docker_lora_adapter_3b"
trainer.model.save_pretrained(adapter_path)
tokenizer.save_pretrained(adapter_path)
```

В папке находятся конфигурация адаптера, его веса и токенизатор. Это не полная копия Qwen-модели. Поэтому адаптер нельзя использовать отдельно: для работы ему нужна исходная базовая модель `Qwen/Qwen2.5-3B-Instruct`.

```text
Qwen/Qwen2.5-3B-Instruct       ← большая базовая модель
my_docker_lora_adapter_3b/    ← небольшой обученный адаптер
```

## 6. Проверка обученного адаптера

Для проверки сначала загружается базовая модель:

```python
base_model = AutoModelForCausalLM.from_pretrained(...)
```

Затем к ней подключается адаптер:

```python
model = PeftModel.from_pretrained(base_model, ADAPTER_PATH)
```

После этого запрос проходит через комбинацию базовой модели и адаптера. Если написать технический вопрос про Docker или FastAPI, модель должна использовать выученную специализацию.

## 7. Запуск через vLLM

Для постоянной работы модель запускается в Colab через vLLM.

При запуске указываются:

```text
--model Qwen/Qwen2.5-3B-Instruct
--enable-lora
--lora-modules docker_adapter=./my_docker_lora_adapter_3b
```

Это означает:

1. vLLM загружает базовую Qwen-модель в память GPU;
2. регистрирует адаптер под именем `docker_adapter`;
3. принимает запросы через OpenAI-совместимый endpoint;
4. применяет адаптер, когда в запросе указано имя `docker_adapter`.

Внутренний запрос выглядит примерно так:

```json
{
  "model": "docker_adapter",
  "messages": [
    {"role": "user", "content": "Как написать Dockerfile для FastAPI?"}
  ]
}
```

vLLM нужен для эффективного инференса: он управляет загрузкой модели, GPU-памятью, очередью запросов и KV-кэшем. Но vLLM не обучает модель — он только использует уже обученную базовую модель вместе с адаптером.

## 8. Как запрос попадает от клиента к модели

Полный путь запроса такой:

```text
1. Клиент отправляет запрос в FastAPI на localhost:8000
2. FastAPI создаёт Celery-задачу
3. RabbitMQ хранит задачу в очереди
4. Celery worker получает задачу
5. worker отправляет HTTP-запрос через ngrok в Colab
6. FastAPI-wrapper в Colab передаёт запрос в vLLM
7. vLLM генерирует ответ через Qwen + LoRA
8. Ответ возвращается обратно через ngrok и Celery
9. Клиент получает результат или проверяет его по task_id
```

Локальная часть не выполняет тяжёлую генерацию. Она отвечает за API, очередь и маршрутизацию задач, а GPU-инференс выполняется в Colab.

## 9. Что делает Gemini-судья

Пакетная оценка — это отдельный процесс проверки качества.

Для пачки промптов система:

1. отправляет несколько запросов модели через Celery;
2. собирает ответы;
3. добавляет эталонные ответы;
4. отправляет всё в Gemini;
5. получает оценку от 1 до 5 и объяснение;
6. сохраняет результат в `eval_report.json`.

Gemini в этой схеме не обучает Qwen. Он только оценивает, насколько ответы обученной модели похожи по качеству на ожидаемые ответы.

```text
Qwen + LoRA → генерирует ответы
Gemini       → оценивает ответы
```

## Главное резюме

Ваш проект работает по принципу адаптации готовой модели:

```text
датасет
  ↓
обучаются маленькие LoRA-матрицы
  ↓
сохраняется только адаптер
  ↓
адаптер подключается к базовой Qwen-модели
  ↓
vLLM запускает модель на T4
  ↓
локальный FastAPI и Celery отправляют запросы в Colab
  ↓
Gemini отдельно оценивает качество ответов
```

Самая важная мысль: вы не создали новую модель с нуля и не переписали всю Qwen. Вы взяли готовую модель, обучили небольшой адаптер под свои технические темы и подключаете этот адаптер к базовой модели во время инференса.
